### E3 — does the UI use the extra width? (measured twice, on purpose)

The first pass reported 454 as identical to 384, and a later pass reported 466 as identical to 454 —
both are the signature of a **stale frame**, not a measurement. `_workbench/measure_profile.py` makes
freshness mechanical: poll `dumpsys window displays` until `cur=`/`app=` match the target, then require
the measured bbox to differ from the previous profile's value, then require two consecutive dumps to
agree, and refuse to report otherwise. Every row below passed all three:

```
=== 384x384 @320 = 192.0 dp ===   space: cur=384x384 app=384x384
   fresh after 3s: 264x96 px (x 60..324)   stable: 132.0 dp (68.8% of 384)
=== 454x454 @320 = 227.0 dp ===   space: cur=454x454 app=454x454
   fresh after 3s: 326x96 px (x 64..390)   stable: 163.0 dp (71.8% of 454)
=== 466x466 @326 = 228.7 dp ===   space: cur=466x466 app=466x466
   fresh after 3s: 338x97 px (x 64..402)   stable: 165.9 dp (72.5% of 466)
=== 480x480 @360 = 213.3 dp ===   space: cur=480x480 app=480x480
   fresh after 3s: 336x108 px (x 72..408)  stable: 149.3 dp (70.0% of 480)
=== 400x400 @320 = 200.0 dp ===   space: cur=400x400 app=400x400
   fresh after 3s: 276x96 px (x 62..338)   stable: 138.0 dp (69.0% of 400)
```

| Profile | Screen | Text column | % of width | Answer card | % of width |
|---|---|---|---|---|---|
| small round | 384 px @320 = 192.0 dp | 264 px = 132.0 dp | 68.8 % | 264 px = 132.0 dp | 68.8 % |
| large round | 454 px @320 = 227.0 dp | 326 px = 163.0 dp | 71.8 % | 326 px = 163.0 dp | 71.8 % |
| **Xiaomi Watch 2** | 466 px @326 = **228.7 dp** | **338 px = 165.9 dp** | **72.5 %** | **338 px = 165.9 dp** | **72.5 %** |
| 480 round | 480 px @360 = 213.3 dp | 336 px = 149.3 dp | 70.0 % | 336 px = 149.3 dp | 70.0 % |
| rectangular | 400 px @320 = 200.0 dp | 276 px = 138.0 dp | 69.0 % | 276 px = 138.0 dp | 69.0 % |

The two columns agree **exactly** at every profile. They are independently laid out elements (the
composer's `EditText` and the answer card's `Text`, both `fillMaxWidth().padding(horizontal = 8.dp)`),
so this agreement is a cross-check that the measurement is reading the thing it claims to read.

An earlier `answer_matrix.py` pass reported 466 and 480 as "answer not on screen" while the composer
still held the typed question — i.e. the ask had not finished, not that the card was missing. The
re-run (`_workbench/answer_card.py`) waits for an answer node whose width **differs** from the previous
profile's, and omits the row instead of reporting a stale one when it cannot observe it.

The column grows with the screen and its *share* of the width grows too, so the extra 36.7 dp of a
Xiaomi Watch 2 is used for text rather than thrown away in margin. No layout change was warranted;
the earlier "fixed 8 dp inset wastes the width" finding was an artifact of the stale dump and is
recorded here as a discarded hypothesis, not a fix.

On-device attempt, watch side, real code path (`WearPairing.request` → `WearPairingTransport`):

```
$ adb -s emulator-5554 logcat -s HermesWear:*
W HermesWear: pairing: no node advertises hermes_phone
```

That is `CapabilityClient.FILTER_REACHABLE` returning zero nodes, which is the documented
consequence of `Accounts: 0` on both emulators: the Wear OS Data Layer needs both devices on the same
Google account (or a real paired phone). The UI reports it honestly:

```
$ adb -s emulator-5554 shell uiautomator dump   # after tapping "Pair with phone"
TextView  [36,110][348,194]  'No phone app found. Install it and open it once, or use a key on the watch.'
```

**Options, evaluated (prompt's A–D):**

| Option | What it would actually prove | Verdict here |
|---|---|---|
| A. Add the same Google account to both emulators | the real Data Layer transport | Not attempted: requires GUI sign-in into a Google account inside two sandboxes. Out of scope for this session, and the account is the owner's. |
| B. Physical devices (Xiaomi Watch 2 + phone) | the real transport, on the real hardware | Out of this session's reach (no hardware attached). This is HS4, unchanged. |
| C. Fake transport + `MessageEvent` tests for the listener | every *decision* branch (no phone / send failed / timeout / ack), not the transport | **Already in place and green:** `WearPairingTest` — 8 tests covering exactly those branches. |
| D. Mock and claim "pairing proved" | nothing | Refused. Not done anywhere in this report. |

**What is proved:** the watch's decision logic (8 unit tests), the honest UI state when no phone is
reachable, and the signing identity both APKs must share. **What is not proved:** the Data Layer
transport itself, phone → watch. HS4 stays recorded as needing hardware.
